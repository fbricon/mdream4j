# mdream4j parity review — 2026-11

Review of the Java port against upstream Rust `mdream` at `9ea07b84` (mdream 2.0.3 plus the
thirteen post-release commits merged on `main`).
Parity contract: byte-identical Markdown/text/HTML/metadata output, plus the three
documented deviations (lone surrogates → U+FFFD, `wrapWidth` counted in code points,
`maxNodeBytes` counted in UTF-8 bytes).

Status legend: `[ ]` todo, `[x]` done.

## Sync to upstream `9ea07b84`

The parity target moved from the npm `2.0.3` state (`55937d7c`) to `main` at `9ea07b84`, which
adds thirteen commits. Each portable fix below was translated 1:1; the two that only touch the
JavaScript package or performance were skipped as noted.

- [x] **#386 — empty heading in a list item.** A heading whose inline children render empty inside
      `<li>` must be written as a bare `- ###`, not dropped or merged into the item marker.
      Ported the heading-marker emission and the following blank-line handling in `OutputOps`.
- [x] **#420 — keep parent item text outside a closed quote.** Added the
      `CAPTION_BOUNDARY_QUOTE_PARENT` / `QUOTE_TENTATIVE` states plus the `QUOTE_CLOSED` sentinel
      and the settle/restore/close helpers, so text after a `</blockquote>` inside a list item is
      rendered in the parent item instead of being captured by the quote.
- [x] **#445 — code fences after a closed quote in a list item.** Added
      `settleQuoteBoundaryAtFence` and `dropEmptyFenceReservation`; the fence now opens at the
      item's indent rather than inside the closed quote.
- [x] **#446 — keep a line's block lead whole when draining.** `drainStreamedPrefix` now calls
      `uncutBlockLeadStart` and holds a lead-only line (`- `, `1. `, `### `) back so
      `opensBlockLine` can still read it from its start. This is what fixes the spurious `\###`
      escapes at chunk boundaries.
- [x] **#448 — list item hard-break indent across a drained marker line.** `truncateBuffer`
      rebases the held hard-break offset when the marker line leaves the buffer; regression test
      added in `StreamingDrainTest`.
- [x] **#450 — move quote frames past an empty item's blank line.** The empty-item separator is
      shifted so a following quote opens at the right depth.
- [x] **#447 — raw HTML block escaping.** Already correct in Java; verified against the reference.
- [x] **#449 — redundant escape after a rule run.** Already present (`splitPoint`
      `afterRuleRun`); verified against the reference.
- [ ] **#444 — heading marker checks linear.** Performance-only, no output change; deferred.
- [ ] **#451 — drop a div heading-marker memo on rewrite.** JavaScript-only; no core equivalent.

Two Java-only defects surfaced while closing the differential and were fixed alongside:

- **Uppercase rawtext end tags.** `ParseOps.canCompleteRawEndTag` compared bytes case-sensitively,
  so `<STYLE>…</STYLE>` (and `<TEXTAREA>`) spanning a chunk boundary was held forever and the tail
  of the document was lost in streaming. It now compares ASCII case-insensitively, matching the
  tokenizer's `matches_opaque_tag`.
- **Drain hold interactions.** The enter-side boundary clear after `recordEnterMarker`, the
  `pendingRawHtmlBoundary` reset on `TAG_LI` exit, capturing `rawHtmlQuoteBoundary` before
  `writeOutput`, `endLink` on every anchor exit, the `TAG_BLOCKQUOTE` enter-output exclusions, and
  the suppression of a space-plus-backtick pair under `QUOTE_PARENT` keep the buffer state
  consistent with the one-shot output across drain points.

Verification of the new pin (reproducible with `tools/reference/src/bin/stream_golden.rs`):

| Differential | Cases | Mismatches |
|---|---:|---:|
| One-shot (markdown) | 2,517 | 0 |
| Streaming (chunk 1 and 7) | 5,034 | 0 |

The corpus was re-extracted (1,190 → 1,218 cases) and `golden/corpus.jsonl` regenerated with the
reference at `9ea07b84`; `./mvnw -q -o -pl mdream4j test` passes (195 tests).

## Confirmed parity bugs

- [x] **Override application at parse time.** Rust (`parse.rs:1237-1252`) applies only
      `is_inline` from a tag override; `collapseInnerWhiteSpace` and `spacing` are resolved
      when the node is rendered. Java also overrode those two node fields in
      `ParseOps.enterOpeningTag`, so `collapseInnerWhiteSpace` folded text early and
      spacing overrides leaked into paths that should use built-in spacing.
- [x] **Override lookup for aliased / custom tags.** Rust picks the override key as
      `TAG_NAMES[tag_id]` only when the tag is built-in, otherwise the source tag name
      (`parse.rs:1244-1247`). Java looked up by `tagId` whenever it was `>= 0`, so a custom
      element that aliased to a built-in tag picked up the built-in tag's override instead
      of its own.
- [x] **`spacing: [0, 0]` override is ignored.** `TagOverride` stores spacing as two ints
      defaulting to `0`, and `spacingOverride()` treats `0/0` as "unset". Rust's
      `spacing: Option<[u8; 2]>` distinguishes `None` from `Some([0, 0])`.
- [x] **`<tr>` row opener deferral ignores overrides.** Rust only defers the row opener when
      the override has neither `enter` nor `exit` (`output.rs:1446-1452`); Java deferred
      unconditionally, so an overridden `<tr>` still emitted the table row opener.
- [x] **Enter marker bookkeeping in the full path.** Rust passes
      `tag_id.filter(|&id| !enter_is_literal && (id != TAG_CODE || code_span_marker_ok()))`
      and `keeps_markers = tag_id == TAG_A && clean.emptyLinkText` (`output.rs:1884-1889`).
      Java passed `tagId` unconditionally and `false`.
- [x] **`clean.emptyLinks` missing on the full enter path.** Rust drops non-navigable `href`s
      in both the simple and full enter emitters (`output.rs:1178-1192`, `1624-1640`);
      Java only had it in `emitEnterSimple`.
- [x] **`<pre>` content inside a list is not clamped to the node byte budget.** Rust clamps
      the indented fenced-code text to the remaining `maxNodeBytes` and sets `truncated`
      (`output.rs:2966-3003`). Java built the indented text unbounded.
- [x] **Extraction `textContent` trim.** Rust uses Unicode `str::trim()`
      (`parse.rs:1581`); Java used `String.trim()` (ASCII controls only).
- [x] **Selector whitespace trim.** Rust `selector.rs:37,54,68,77` uses Unicode `str::trim()`;
      Java used `Chars.trimAscii()`. Attribute-selector internals correctly stay
      `trim_ascii` (`selector.rs:140,148,157`).

## Performance / hygiene

- [x] `OutputOps.textRunRoom` — the O(1) rewrite was reverted because it changed JIT inlining
      and made `text-10mb` ~60% slower (9.14 ms → 14.6 ms, reproducible A/B). The original scan
      is linear for drainable runs, but **quadratic when a run cannot be split** (non-batchable
      text such as `&`, plus `<pre>`, blockquotes, headings and titled links): 488 KB of
      `&amp;` took 4.0 s against 4 ms for the Rust reference. Fixed by caching the parse
      buffer's UTF-8 length and extending it per append
      (`ConvertState.textBufferMeasuredLength` / `textBufferMeasuredBytes`), which is amortised
      O(1) and leaves the output byte-identical. `ScalingRegressionTest` guards it.
- [x] The per-character `maxNodeBytes` check reused the same full scan, so enabling the
      documented untrusted-input cap amplified the quadratic (98 KB of `&` with a 1 MB cap took
      771 ms vs 0.9 ms uncapped). It now uses the cached length as well.
- [x] **Streaming tokens that span chunks were quadratic.** `ConverterStream` carried the raw
      unconsumed tail and re-fed it on every `feed`, so an unterminated start-tag name, end-tag
      name, or quoted attribute value copied and rescanned the whole growing prefix once per
      chunk. The tokenizer now consumes those bytes into state (`ConvertState.pendingTagName`,
      `pendingCloseTagName`, and the incremental `TagCarry.nameBytes` / `valueBytes` counters)
      and resumes from the saved tokenizer position, so the carried tail stays empty and the
      work is linear. `finalizeState` rebuilds the raw prefix at EOF, which keeps the residual
      (rawtext text and `truncated`) handling identical. Measured with 1 KiB feeds:

      | Input | before | after (median of 3) |
      |---|---:|---:|
      | `</` + `x`, 4 MiB | 8,383 ms | 24 ms |
      | `<` + `x`, 8 MiB | 7,288 ms | 24 ms |
      | `<a href="` + `x`, 16 MiB | 19,773 ms | 39 ms |

      Output is unchanged: a 6,443-case differential (one-shot vs 1 KiB and char feeds, caps,
      tag overrides, malformed fuzz) matches the pre-change classes byte for byte, including
      `truncated`. `ScalingRegressionTest` now guards 8 MiB / 4 MiB / 16 MiB feeds and
      every-split equivalence for spanning names.
- [ ] `ParseOps.pushCappedTextNode` still rescans `scriptTextBuffer` (extraction-only, and
      flushed per script element); the parse buffer uses the cached length. Deferred.
- [x] `Scan.pushAttr` allocates a `getBytes()` array per attribute.
- [x] `Url` has an unbounded `indexOf` walk and repeated `getBytes()`/`utf8Length` calls.
- [ ] Boxed `List<Integer>` state left in `ConvertState`.
- [x] Dead self-assignment (`override.selfClosing() != null) { tag.isNonNesting = tag.isNonNesting; }`).

## Performance check (2026-11)

Comparing against the numbers frozen in `docs/BENCHMARKS.md` is misleading in two ways: that
table is rounded (2 decimal MB for allocation, 3 significant digits for time) and those values
are single runs, not a controlled comparison. This check therefore uses an **interleaved A/B**:
the pre-change and post-change jars are built once, then run alternately (baseline, current,
baseline, current) with identical JMH settings on the same machine and JDK
(`-wi 3 -w 1 -i 5 -r 1 -f 2 -prof gc`, Temurin 25.0.4.1, macOS arm64). The tables below are the
means of the two rounds; `Δ` is the mean of the two per-round deltas, so drift affects both
sides.

### Time (`avgt`, ms/op, lower is better)

| Fixture | baseline | current | Δ | resolving? |
|---|---:|---:|---:|---|
| nuxt (3.5 KB) | 0.0095 | 0.0094 | -0.9% | no — ±0.4 µs error on 9.5 µs |
| depth-512 | 0.0597 | 0.0603 | +1.0% | no — ±3% run-to-run |
| node-1mb | 0.925 | 0.919 | -0.6% | no |
| table-huge | 3.516 | 3.511 | -0.2% | no |
| text-10mb | 9.83 | 9.75 | -0.8% | no — sign flips between rounds |
| vuejs-docs | 0.388 | 0.368 | -5.1% | weak — both rounds negative |
| wikipedia | 0.756 | 0.708 | -6.3% | weak — both rounds negative |
| mdn | 1.363 | 1.319 | -3.2% | weak |
| react | 0.768 | 0.740 | -3.6% | weak |
| github | 0.890 | 0.857 | -3.6% | marginal — -6.5% then -0.7% |
| wikipedia-xl | 12.50 | 12.00 | -4.0% | yes — both rounds -4%, errors ~3% |

Allocation is the one metric with a real error bar: JMH reports `gc.alloc.rate.norm` to within
~0.2 B/op, so those deltas are genuine. Only fixtures with many attributes moved (-1 to -2.7%),
which matches the `attr_bit(CharSequence)` / `Url.stripTrackingParams` allocation removals; the
synthetic fixtures allocate byte-for-byte the same. This is also why comparing against the
recorded `0.02` MB for `nuxt` produced a bogus `+23%` — 24,600 B/op rounds to 0.02 MB, so the
baseline was only known to ±0.005 MB.

The streaming fix was re-checked the same way on `wikipedia`, `github`, and `text-10mb`: time
moved by -2.0% to +0.5% and allocation by 0.0% on all three (the first cut allocated a result
object per start tag, which was visible as +2.4% B/op; reusing one result object removed it).

**Verdict:** no regression anywhere. Time is flat to within noise on the synthetic fixtures and
3–6% faster on the real pages, though at ~±3% run-to-run error only `wikipedia-xl` actively
clears the bar; treat the smaller real-page wins as "probably a little faster, not proven".
Allocation is the solid result: unchanged on synthetic input, down 1–2.7% on real pages.

## Deferred

The remaining performance items are bounded in practice: `pushCappedTextNode` /
`pushCodeSpanContent` only rescans a drained (<64 KiB) or capped buffer, and the boxed
`List<Integer>` state would need a primitive collection or hand-rolled int stack. Both are
polish, not parity or scaling risks, so they are left as follow-ups.

Regression coverage for the parity fixes lives in
`mdream4j/src/test/java/io/github/fbricon/mdream4j/TagOverrideParityTest.java` (expected strings
recorded from the Rust reference) plus `ConstsTest` and `PluginsTest`.
